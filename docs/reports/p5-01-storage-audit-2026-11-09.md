## SQLite leaks and backend-specific behavior

- `AppState.pool` is a public `SqlitePool`. HTTP directly begins transactions and imports SQLite helpers for auth, device CRUD, audit, telemetry queries, attributes and overview/readiness.
- MQTT stores/passes `SqlitePool` to `AuthHooks`, `PresenceHooks`, kick recovery, the SQLite attribute worker and `SqliteCommandRepository`; runtime/supervisor constructs both current repositories and migration/pool; retention takes `SqlitePool` directly. The storage adapter is therefore not the sole DB boundary.
- Existing core ports: `CommandRepository` is broad and domain-facing; `TelemetryRepository` only abstracts batch insert. No ports yet cover admin/session, device CRUD/auth, telemetry query/checkpoint/retention, attributes, overview or storage health.
- SQLite-specific details to isolate: `SqlitePool`/`SqliteConnection`/`QueryBuilder<Sqlite>`, `BEGIN IMMEDIATE`, `INSERT OR IGNORE`, `ON CONFLICT ... excluded`, `INDEXED BY`, `sqlite_sequence`, `AUTOINCREMENT`, `STRICT`, partial unique index, SQLite JSON1 (`json_each`/`json_valid`/`json_type`), `instr`/`lower`, `?` bind syntax, boolean/integer mapping, and `RETURNING`/`rows_affected` assumptions. SQLite PRAGMAs (WAL, FULL, foreign keys, busy timeout, checkpoint) are per-connection setup, not a domain contract.

## Minimum port boundaries (decision for P5-02 design)

Use domain operations, not a generic SQL/ORM layer:

1. Add an admin/auth repository for user lookup, bootstrap, session lifecycle/cleanup and login/logout audit boundaries.
2. Add a device repository for CRUD, active-credential lookup, last-seen and mutation operations that own their atomic audit writes.
3. Keep `CommandRepository`; keep/expand `TelemetryRepository` for ingest, query/checkpoint and retention; add a small attributes repository.
4. Put overview aggregation and DB health behind small read/health ports. Keep migrations and pool construction in backend adapters/runtime, never in `core`.
5. Keep runtime-config persistence on its filesystem implementation. Its post-rename audit remains best-effort and separate; do not pass SQL transactions across ports. Device/admin/command mutation audit stays in the same repository operation/transaction as its mutation.

This is a boundary decision, not a request to scaffold these ports in P5-01. PostgreSQL features, URL and engine version were selected later in ADR-010.

## Telemetry checkpoint decision and evidence

`docs/plans/02-contracts.md` §3.3/§4.4 now defines a committed-prefix checkpoint and explicitly permits non-row allocator gaps from ignored inserts. The current SQLite implementation is safe because production has one telemetry writer and `BEGIN IMMEDIATE` holds SQLite's single-writer reservation through ID allocation and commit; uncommitted `sqlite_sequence` state is not visible to another connection. `ignored_duplicate_and_conflict_advance_checkpoint_without_backfill_rows` proves the duplicate/conflict result, empty backfill across the advanced checkpoint, and recovery of a later stored row. `sqlite_commit_checkpoint_serializes_competing_writers_and_backfills_both` holds T1 after insertion, proves T2 cannot begin/allocate while T1 is open, observes a checkpoint that excludes T1, then commits T1/T2 and verifies both rows page in increasing ID order. It also rolls back a reserved T1, verifies the checkpoint stays fixed, and proves a later T2 write is recovered. Existing `commit_checkpoint_does_not_advance_past_an_uncommitted_batch` covers the no-uncommitted-row visibility case.

For PostgreSQL, use a transactionally serialized allocator/checkpoint (e.g. lock/update a durable allocator row before assigning event IDs and hold that lock through commit). A nontransactional sequence/identity/auto-increment can reserve a lower ID for a transaction that commits after a higher ID and is not sufficient. Duplicate/conflict attempts may leave non-row allocator gaps as long as the committed-prefix property holds. PostgreSQL must run the same T1/T2/backfill plus rollback vector before its A18 gate.
